# EkoNiva Project 2

## Что это за проект
Веб-приложение на Streamlit для прогноза структуры стада по историческим событиям:
- осеменения;
- отёлы и рождения;
- запуск;
- выбытие;
- справочник быков.

Приложение умеет работать в двух основных режимах:
- прогноз по одному подразделению;
- прогноз по хозяйству как сумме нескольких подразделений.

Отдельно реализованы:
- историческая проверка качества прогноза по подразделениям и хозяйствам;
- редактирование параметров модели в админ-режиме;
- ограничения по скотоместам;
- рекомендации по переводам между подразделениями;
- Excel-выгрузка результатов;
- кэш параметров и кэш прогнозов в PostgreSQL.

## Основные сценарии в интерфейсе
### 1. Прогноз по одному подразделению
Пользователь выбирает подразделение из БД или загружает файлы вручную и получает:
- прогноз по группам животных;
- переполнение по группам;
- backtesting;
- Excel-выгрузку;
- просмотр и изменение скотомест для выбранного подразделения.

### 2. Параметры
Вкладка показывает, какие параметры используются для расчёта:
- длительность стельности и сухостоя;
- параметры осеменения;
- параметры выбытия;
- доли использования типов семени;
- доли рождаемости бычков и тёлочек.

В админ-режиме параметры можно менять для выбранного подразделения и сохранять как runtime override.

### 3. Прогноз по хозяйствам
Вкладка предназначена для пакетной работы по нескольким подразделениям одного хозяйства:
- загрузка комплектов файлов;
- запись и обновление данных в БД;
- расчёт прогноза по каждому подразделению;
- агрегация прогноза на уровень хозяйства;
- backtesting по хозяйству;
- рекомендации по переводам между подразделениями;
- настройка скотомест по группам и по подразделениям.

## Как считается прогноз
### Базовая идея
На дату последнего события в данных строится стартовое состояние стада. После этого модель прокручивает стадо по дням до целевого месяца.

### Что происходит в симуляции
- животные стареют;
- у коров растёт DIM;
- открытые животные переходят в осеменение;
- часть осеменений становится стельностью;
- стельные коровы переводятся в сухостой;
- происходят отёлы;
- рождаются тёлочки и бычки;
- животные выбывают;
- в конце месяца проверяются ограничения по скотоместам.

### Как устроено состояние стада
Внутри расчёта используются агрегированные `numpy`-массивы:
- коровы по лактациям и DIM;
- стельные коровы по дням до отёла;
- нетели по дням до отёла;
- тёлки по возрасту;
- бычки по возрасту.

Переход в следующую лактацию происходит в момент отёла: корова выходит из массива стельных текущей лактации и попадает в `open` следующей лактации с `DIM = 0`.

### Что влияет на прогноз
- исторические параметры подразделения;
- параметры выбытия;
- доли sexed/traditional semen;
- соотношение бычков и тёлочек;
- ограничения по скотоместам;
- пользовательские overrides в админ-режиме.

## Поток данных
1. Пользователь загружает файлы Excel и TXT.
2. ETL-модули читают файлы и приводят колонки к единому формату.
3. Данные очищаются и записываются в PostgreSQL.
4. По загруженным таблицам считаются параметры подразделения.
5. Параметры кэшируются в таблице `model_params_cache`.
6. Прогноз считается динамической моделью.
7. Для вкладки хозяйств результат кэшируется в `tab3_forecast_cache`.
8. Результат выводится в Streamlit и при необходимости выгружается в Excel.

## Быстрый запуск
### Docker
```bash
docker compose up --build
```

После запуска:
- приложение: `http://localhost:8510`
- PostgreSQL: `localhost:15432`

### Локальный запуск
```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
streamlit run app.py
```

### Переменные окружения
- `POSTGRES_DSN` — строка подключения к PostgreSQL.
- `ADMIN_KEY` — ключ входа в админ-режим.

## Структура проекта

### Корень репозитория
- `README.md` — документация по проекту, структуре, запуску и ролям файлов.
- `app.py` — главная точка входа Streamlit. Настраивает страницу, включает админ-режим и подключает три вкладки интерфейса.
- `config.py` — читает `POSTGRES_DSN` из окружения и задаёт дефолтное подключение для Docker-окружения.
- `db.py` — создаёт единый SQLAlchemy `engine`, который используется всеми модулями проекта.
- `forecast.py` — верхнеуровневая обёртка над динамическим движком. Используется для расчёта из БД и для части fallback/агрегирующей логики вокруг месячных метрик.
- `forecast_dynamic.py` — основной движок модели. Здесь находятся построение стартового состояния стада, дневная симуляция, расчёт birth-метрик, ограничений по вместимости и итогового прогноза.
- `forecast_dynamic_normalization.py` — функции нормализации идентификаторов, событий, пола, результата осеменения и работы с типами семени. Это тонкий слой подготовки значений для движка прогноза.
- `params_runtime.py` — вычисление параметров модели по историческим данным. Считает параметры осеменения, длительность стельности, сухостоя, профиль выбытия и вспомогательную мета-информацию.
- `sales_policy.py` — отдельная политика реализации по вместимости. На текущий момент содержит dataclass с решением о продаже/реализации и функцию применения лимитов по группам.
- `makefile` — короткие команды для пересборки Docker-окружения.
- `Dockerfile` — образ приложения Streamlit.
- `docker-compose.yml` — поднимает приложение и PostgreSQL.
- `db/init.sql` — базовая схема raw-таблиц PostgreSQL для событий и справочника быков.
- `requirements.txt` — Python-зависимости проекта.

### Папка `core/`
- `core/__init__.py` — пакетный маркер.
- `core/backtesting.py` — общий слой исторической проверки прогноза:
  - расчёт факта по выбранной метрике;
  - проверка полноты месяца;
  - извлечение прогнозного значения для backtesting;
  - единые формулы процентной ошибки для `tab1` и `tab3`.
- `core/constants.py` — список индикаторов прогноза, колонок переполнения и маппинг между индикатором и колонкой переполнения.
- `core/date_parse.py` — безопасный парсер дат для смешанных форматов (`DD.MM.YYYY`, `YYYY-MM-DD`, datetime-строки из Excel). Используется ETL и вычислением параметров.
- `core/helpers.py` — общие утилиты по датам, нормализации имён показателей и безопасному чтению значений из словарей результата.
- `core/calving_facts.py` — расчёт факта по отёлам и рождениям из DataFrame-таблиц. Используется в backtesting и при overlay фактических данных на первый месяц прогноза.
- `core/params.py` — центральный слой работы с параметрами:
  - расчёт параметров из БД и из таблиц;
  - кэширование в `model_params_cache`;
  - объединение дефолтов, вычисленных параметров и admin overrides;
  - подстановка актуальных параметров по семени из загруженных данных;
  - загрузка параметров в `session_state`;
  - очистка кэша по подразделению и сохранение параметров по текущей сигнатуре данных.
- `core/realization.py` — построение плана ранней реализации по результатам прогноза и переполнениям.
- `core/excel_export.py` — сборка Excel-файлов для выгрузки прогноза, переполнений и плана реализации.

### Папка `etl/`
- `etl/__init__.py` — пакетный маркер.
- `etl/calvings_births.py` — парсер файла отёлов и рождений:
  - распознаёт шапку Excel;
  - ищет аналоги нужных колонок по алиасам;
  - разворачивает `CALF1..CALF5` в строки рождений;
  - корректно парсит даты из разных форматов исходных файлов;
  - сохраняет также `__farm` и `__subdivision`, если они есть в исходнике;
  - содержит функцию загрузки в `calvings_births_raw`.
- `etl/inseminations.py` — парсер файла осеменений:
  - находит шапку;
  - нормализует колонки;
  - очищает даты и числовые поля;
  - поддерживает чтение общего файла хозяйства с полями `__farm` и `__subdivision`;
  - содержит загрузку в `inseminations_raw`.
- `etl/dryoff.py` — парсер файла запусков:
  - читает Excel с вариативной шапкой;
  - приводит поля запуска к единой схеме;
  - очищает даты и числа;
  - содержит загрузку в `dryoff_raw`.
- `etl/disposals.py` — парсер файла выбытий:
  - ищет нужные колонки по алиасам;
  - очищает даты, причины и числовые поля;
  - содержит загрузку в `disposals_raw`.
- `etl/bulls.py` — парсер текстовых файлов с быками. Умеет читать fixed-width и fallback-вариант по split, очищает строки и загружает данные в `bulls_raw`.

### Папка `model_params/`
- `model_params/__init__.py` — экспорт дефолтных параметров пакета.
- `model_params/defaults.py` — базовые константы модели:
  - длительность стельности и сухостоя;
  - дефолтная вместимость по группам;
  - параметры осеменения;
  - параметры выбытия;
  - доли использования типов семени;
  - соотношение бычков и тёлочек.

### Папка `scripts/`
- `scripts/compute_model_params.py` — офлайн-скрипт для расчёта параметров модели напрямую из таблиц БД. По сути это исторический/служебный инструмент для аналитической проверки формул вне Streamlit-интерфейса.

### Папка `ui/`
- `ui/__init__.py` — пакетный маркер.
- `ui/styles.py` — оформление таблиц Streamlit: форматирование чисел, подсветка негативных значений и стили для переполнений.
- `ui/tab1_forecast.py` — вкладка прогноза по одному подразделению:
  - выбор режима работы из БД или по загруженным файлам;
  - фильтрация по хозяйству и подразделению;
  - запуск расчёта;
  - backtesting по выбранной метрике;
  - выгрузка Excel;
  - просмотр и редактирование скотомест для выбранного подразделения;
  - показ последней даты в загруженных данных и очистка кэша параметров выбранного подразделения.
- `ui/tab2_params.py` — вкладка параметров:
  - показывает итоговые параметры для текущего scope;
  - умеет отображать их в read-only виде;
  - в админ-режиме позволяет изменять параметры и сохранять overrides;
  - умеет возвращать параметры к значениям по умолчанию;
  - после правки параметров сбрасывает старый прогноз `tab1`, чтобы пользователь не видел устаревший результат.
- `ui/tab3_farm.py` — фасадный файл для вкладки хозяйств. Самой логики почти не содержит: просто реэкспортирует функции из `ui/tab3_farm_parts/`, чтобы остальной проект мог импортировать `ui.tab3_farm` как единый модуль.

### Папка `ui/tab3_farm_parts/`
- `ui/tab3_farm_parts/__init__.py` — пакетный маркер.
- `ui/tab3_farm_parts/common.py` — общий слой для вкладки хозяйств:
  - dataclass `FarmUploadBundle`;
  - fallback-парсеры;
  - группировка загруженных файлов по комплектам;
  - подготовка таблиц для записи в БД;
  - расчёт хэшей параметров и payload;
  - хранение runtime overrides для хозяйств и подразделений.
- `ui/tab3_farm_parts/storage.py` — всё, что связано с БД для вкладки хозяйств:
  - создание служебных таблиц `tab3_*`;
  - запись и удаление комплектов данных;
  - дедупликация;
  - карта `подразделение -> хозяйство`;
  - кэш прогнозов;
  - кэш и хранение скотомест;
  - загрузка данных подразделения или хозяйства из БД;
  - статусы готовности подразделений и хозяйств.
- `ui/tab3_farm_parts/compute.py` — расчётный слой хозяйств:
  - backtesting по хозяйству;
  - агрегация прогноза из подразделений;
  - проверка согласованности суммарного результата;
  - вычисление рекомендаций по переводам;
  - работа с историческими долями и балансом между подразделениями;

  - панель загрузки файлов;

## Что важно знать по данным
- Файлы по осеменениям могут быть общими на всё хозяйство, поэтому для корректной работы критично поле подразделения в исходном Excel.
- Файлы быков могут загружаться отдельно по подразделениям.
- Для корректного расчёта по подразделению нужны данные минимум по отёлам, осеменениям, запуску и выбытиям.
- Параметры считаются отдельно для каждого подразделения и кэшируются по сигнатуре его таблиц.

## Кэширование
- Параметры подразделения не пересчитываются на каждый запуск. Если сигнатура таблиц не изменилась, они берутся из `model_params_cache`.
- Прогнозы хозяйств кэшируются в `tab3_forecast_cache`.
- После перезагрузки данных нужные кэши очищаются автоматически в логике загрузки, а для выбранного подразделения кэш параметров можно очистить отдельно из интерфейса.

## Что стоит редактировать с осторожностью
- `forecast_dynamic.py` — любое изменение влияет сразу на все прогнозы и backtesting.
- `params_runtime.py` — изменение формул меняет все автоматически вычисленные параметры.
- `ui/tab3_farm_parts/storage.py` — здесь хранится логика автоматического обновления БД, дедупликации и маппинга хозяйств/подразделений.
- `etl/*.py` — ошибки в этих файлах дают неочевидные искажения уже на этапе данных, которые потом выглядят как “плохой прогноз”.

## Текущий принцип расширения проекта
Если нужно добавить новый тип отчёта или новую вкладку, лучше придерживаться уже используемой схемы:
- ETL и нормализация отдельно;
- проверка факта и historical validation отдельно;
- расчёт отдельно;
- доступ к БД отдельно;
- UI отдельно.

Именно поэтому логика `tab3` уже разнесена на `common.py`, `storage.py`, `compute.py` и `ui_components.py`.
